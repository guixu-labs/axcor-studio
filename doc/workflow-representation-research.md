# 工作流表达方式调研与 axcor-studio 设计建议

**整理日期：** 2026-11-06

**调研范围：** 自然语言、声明式配置、代码、可视化编排和业务流程模型。

**材料依据：** 代表产品的官方文档。本调研不覆盖全部产品，也未进行功能、性能或成本实测。

**文档状态：** 调研总结与待评审建议，不构成已批准的实现方案或当前产品能力说明。

## 1. 主要结论

业界常见工作流表达方式可以归纳为五类：自然语言 / Markdown、声明式 DSL、代码、可视化节点与连线、BPMN 业务流程模型。它们存在重叠，实际产品可以同时支持多种方式。

讨论选型时，应分别回答三个问题：用户如何编写、定义如何保存、执行时如何决定下一步。自然语言是描述方式，YAML / JSON 是数据格式，画布是编辑入口，DAG / 状态机则描述执行关系，不能将这些概念直接作为互斥选项比较。

对 axcor-studio 的建议是：围绕“工作流一站式解决平台”定位，支持易读的任务描述与明确的执行约束逐步结合；让同一工作流的编写、执行、观测、评测和团队复用能够关联起来。具体文件格式应服务于这些能力。

## 2. 五类常见表达方式

下表中的产品能力来自官方资料；适用场景和局限是基于其表达机制的分析判断，不是性能排名。

| 表达方式 | 如何表达工作流 | 代表实现与官方依据 | 适用场景 | 主要局限 |
| --- | --- | --- | --- | --- |
| 自然语言 / Markdown | 描述目标、步骤、背景、约束和验收，由 Agent 理解任务 | [GitHub Agentic Workflows](https://docs.github.com/en/copilot/concepts/agent-capabilities/agent-powered-workflows-and-operations/about-github-agentic-workflows) 使用 Markdown 任务说明，并配合结构化配置 | 开发、调查、分析等需要上下文判断的任务；人和 Agent 共同维护流程 | 歧义、执行路径变化和遗漏需要通过约束、验证与人工确认控制 |
| 声明式 DSL：YAML / JSON 等 | 用平台定义的字段声明触发器、任务、依赖、条件、输入输出和失败处理 | [GitHub Actions](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax) 使用 YAML；[AWS Step Functions](https://docs.aws.amazon.com/step-functions/latest/dg/developing-workflows.html) 使用 ASL，具体工具支持 JSON、YAML 等表示形式 | CI/CD、服务编排和需要版本管理、静态校验的自动化 | 表达能力受 DSL 限制；复杂逻辑可能冗长；不同平台字段和语义不通用 |
| 代码：Workflow as Code | 用通用编程语言与工作流 SDK 描述步骤和控制逻辑 | [Temporal](https://docs.temporal.io/workflow-definition) 通过代码定义工作流，支持多种语言 | 复杂业务逻辑、动态编排、工程化测试和代码复用 | 需要编程能力；必须遵守引擎约束，例如 Temporal 的确定性要求 |
| 可视化节点与连线 | 拖拽节点，连接执行关系或数据流，通过表单设置参数 | [n8n](https://docs.n8n.io/build/understand-workflows.md) 将工作流定义为相互连接的节点集合 | 集成自动化、跨角色沟通、流程理解与调试 | 大型流程容易复杂；图形差异审查与多人合并需要专门支持 |
| 标准业务流程模型：BPMN | 用任务、事件、网关、泳道等标准元素建模 | [Camunda](https://docs.camunda.io/docs/components/modeler/bpmn/automating-a-process-using-bpmn/) 执行 BPMN 流程，模型可导出为 [XML 定义](https://docs.camunda.io/docs/8.8/components/modeler/web-modeler/file-download/) | 人工审批、跨部门协作、长周期业务流程 | 需要学习建模语义；可执行范围和扩展能力仍取决于引擎 |

Markdown 不会天然成为可执行工作流，YAML 也不会天然提供可靠执行。必须有工具或引擎规定如何解释文件、调用动作、处理失败和判断完成。

## 3. 区分三个层次

| 层次 | 核心问题 | 常见选择 | 设计时需要明确的内容 |
| --- | --- | --- | --- |
| 编写入口 | 用户如何创建和修改？ | 对话、Markdown、表单、代码编辑器、可视化画布 | 谁负责编辑、如何审查变更、多个入口是否操作同一份定义 |
| 存储与交换格式 | 定义如何保存、版本管理和交换？ | YAML、JSON、Markdown、代码文件、XML | Schema 版本、引用方式、兼容策略、权威源文件 |
| 执行模型 | 下一步如何决定？ | 顺序、DAG、状态机、事件驱动、Agent 动态规划 | 分支、并行、循环、等待、重试、暂停恢复和完成条件 |

这些层次可以组合。例如，一个画布编辑的状态机可以保存为 JSON；一个 YAML 定义的步骤可以调用 Agent，步骤正文仍然是自然语言。

执行模型也可以组合使用：

- **顺序执行：** 前一步完成后进入下一步。
- **DAG：** 根据无环依赖关系调度，适合表达可并行的阶段；包含循环的整体流程不能直接称为 DAG。
- **状态机：** 根据当前状态、结果和事件转移，适合表达等待、重试与恢复。
- **事件驱动：** 由外部事件或消息推动流程，常与状态机结合。
- **Agent 动态规划：** 运行时根据目标和上下文决定后续动作，需要限定权限、预算和停止条件。

## 4. 自然语言的两种作用与混合表达

### 4.1 编写时使用自然语言

用户描述需求，AI 生成 YAML、代码或流程图，经过校验和评审后执行生成的定义。

这种方式降低的是编写门槛。生成结果仍需检查，运行时行为取决于生成内容及其引擎；使用 YAML 并不意味着其中调用的 Agent 或外部服务具有确定性。

### 4.2 运行时解释自然语言

任务说明保留在工作流中，运行时由 Agent 结合上下文理解、选择工具并判断下一步。适合无法预先列举全部分支的任务，但需要独立的验收证据，不能仅以 Agent 声称完成作为成功判据。

### 4.3 混合表达的实际例子

GitHub Agentic Workflows 将文件分成两部分：YAML frontmatter 配置触发器、权限、AI 引擎和允许的输出操作；Markdown 正文描述 Agent 需要完成的任务。工具将该文件编译为 `.lock.yml` GitHub Actions 工作流。[官方结构与编译流程](https://docs.github.com/en/copilot/how-tos/github-agentic-workflows/creating-github-agentic-workflows)

这里的编译并不意味着自然语言中的每个判断都已变成固定分支：运行配置被生成，Agent 仍在运行时解释任务说明。

对平台设计的启示是，可以用结构化字段表达明确的执行边界，用自然语言表达需要理解和判断的任务，两部分共同进入版本管理和审查。

## 5. 对 axcor-studio 的设计建议

以下内容是本次调研形成的建议，需要结合实际用户任务和执行服务契约评审。本次未核对源码以确认其实现状态，也不预设 Codex、Claude Code、OpenCode 在不同运行环境中具有相同能力。

### 5.1 保持易读的源文件，明确结构化边界

现有[方案设计](axcor-studio-design.md)提出以 Markdown 工作流及轻量 frontmatter 组织工作流资产。本次调研可作为该方向的补充依据。

建议保留 Markdown 对目标、上下文和验收的表达能力，逐步明确需要机器校验的内容：

- 工作流标识、版本、输入输出与产物引用。
- 阶段或步骤关系、条件与失败处理。
- 工具或 Agent 绑定、权限范围、超时与重试策略。
- 人工确认点、完成条件和验证证据。

无需一次引入全部字段；优先覆盖真实任务反复出现的约束。哪些内容放在 frontmatter、独立 YAML 文件或运行时配置中，应在具体 Schema 设计时决定。

### 5.2 多种入口共享可追溯的定义

建议让自然语言辅助编写、源文件编辑和流程预览围绕同一工作流版本工作。若引入中间表示，应明确其与源文件的关系，并保留源文件、生成计划和运行记录之间的映射。

| 表达入口或资产 | 建议承担的职责 |
| --- | --- |
| 自然语言 / Markdown | 任务目标、背景、Agent 指令、验收说明 |
| YAML / JSON 等结构化定义 | 可校验的步骤、依赖、输入输出与执行约束 |
| 流程图 | 展示结构、定位当前执行位置；有明确映射后再支持编辑 |
| 代码扩展 | 承载复杂计算和集成逻辑，通过明确接口接入 |
| 运行记录 | 记录实际步骤、工具调用、失败、人工接管、产物和验证结果 |

不应承诺任意代码、自然语言和图形之间无损互转。首期可限定可视化支持的结构，对动态节点展示其边界及实际运行轨迹。

### 5.3 分步验证产品方向

1. **先打通文本定义与运行。** 从自然语言 / Markdown 辅助编写和必要的结构化元数据开始，明确输入、完成条件与错误提示。
2. **提供流程预览和运行定位。** 验证用户是否能理解计划与实际执行的差异，再决定是否增加画布编辑。
3. **按真实需求扩展。** 在出现足够复杂的业务逻辑、人工审批或外部系统兼容需求后，再评估代码 SDK、BPMN 或更多格式。

这一顺序是建议，不代表已承诺的路线图。尤其需要通过原型验证：哪些任务适合固定阶段，哪些节点需要 Agent 自主决策，以及失败后从哪里恢复。

## 6. 后续选型的验证标准

建议选取相近的开发、问题调查和人工确认任务，比较不同表达方式，而不是仅比较文件长度或编辑器外观。

| 维度 | 需要回答的问题 |
| --- | --- |
| 编写与修改成本 | 从需求到可运行定义需要多久？需求变化时需要修改多少位置？ |
| 可理解性 | 接手成员能否说明流程、关键约束和完成条件？ |
| 校验能力 | 能否在运行前发现缺失输入、无效引用和不支持的能力？ |
| 可控性 | 是否明确权限、重试上限、人工确认点和终止条件？ |
| 可观测与恢复 | 能否定位失败步骤、关联证据，并避免恢复时重复产生副作用？ |
| 团队复用 | 能否审查变更、固定版本，并在另一个任务中复用？ |
| 维护成本 | 源文件、图形视图、运行配置是否容易出现不一致？ |

本调研支持表达方式和产品方向的讨论；效率、可靠性及成本收益仍需实际任务验证，不能由某一种文件格式或工具品牌直接推导。
